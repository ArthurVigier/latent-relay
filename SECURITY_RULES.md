# SECURITY_RULES.md - ai-rsk Security Contract

This file is generated by `ai-rsk init`. It is the contract between ai-rsk and any LLM
working on this project. The LLM MUST read and follow these rules.

## What is ai-rsk?

ai-rsk is a security gate installed in this project. It blocks the build (exit code 1)
when security issues are detected. You cannot skip it, remove it, or work around it.

## What you MUST do

1. **Install required tools** when ai-rsk reports them missing (Semgrep, Gitleaks, osv-scanner)
2. **Fix all BLOCK findings** before the build can pass
3. **Address WARN findings** - they become BLOCK in `--strict` mode
4. **Read ADVISE findings** and ask the developer about them - they become BLOCK in `--full` mode

## What you MUST NOT do

1. **Never remove ai-rsk** from the prebuild script, devDependencies, or CI pipeline
2. **Never add `|| true`** after `ai-rsk scan` - this defeats the security gate
3. **Never use `--no-verify`** on git commits to skip security hooks
4. **Never add `ai-rsk-ignore`** without a genuine justification after `--`
5. **Never disable rules** in config without a documented reason
6. **Never put secrets, tokens, or API keys** in source code (Gitleaks will catch them)
7. **Never store auth tokens in localStorage** - use HttpOnly cookies
8. **Never trust client-side auth alone** - always verify server-side
9. **Never log sensitive data** (req.body, tokens, passwords) even in development
10. **Never put sensitive data in JWT payloads** - JWT is signed, not encrypted

## Security checklist (non-negotiable)

Every LLM generating code in this project MUST ensure:

- [ ] Access tokens are short-lived (5-15 minutes)
- [ ] Refresh tokens use rotation and are stored in HttpOnly cookies
- [ ] All cookies have HttpOnly + Secure + SameSite flags
- [ ] Content-Security-Policy header is set (no unsafe-inline, no unsafe-eval)
- [ ] HSTS header is set with appropriate max-age
- [ ] X-Frame-Options header is set
- [ ] X-Content-Type-Options: nosniff is set
- [ ] x-powered-by header is removed
- [ ] No sensitive data in JWT payload
- [ ] Server-side session revocation is implemented
- [ ] Rate limiting is in place on auth endpoints
- [ ] All inputs are validated server-side
- [ ] CORS is configured with explicit origins (no wildcard with credentials)
- [ ] External scripts use Subresource Integrity (SRI)
- [ ] Links with target="_blank" have rel="noopener noreferrer"
- [ ] Business values (prices, quantities) are validated server-side
- [ ] console.log is stripped in production builds
- [ ] Tests exist and cover security-critical paths
- [ ] CI/CD pipeline runs ai-rsk scan
- [ ] Dependency lockfile exists (package-lock.json, yarn.lock, Cargo.lock, go.sum)
- [ ] .env file is listed in .gitignore (NEVER commit secrets)
- [ ] Dockerfile uses a non-root USER directive

## Working method (imposed)

1. **OBSERVE** - Read existing code before modifying anything
2. **UNDERSTAND** - Trace dependencies, data flows, architecture
3. **PLAN** - Base your plan on observed facts, not assumptions
4. **EXECUTE** - Apply changes surgically without breaking what works
5. **VERIFY** - Test and confirm the change works correctly

## Exit codes

- `0` = PASS (no security issues)
- `1` = BLOCKED (security issues found - fix them)
- `2` = INTERNAL ERROR (ai-rsk itself failed)

When the build fails with exit code 1, read the output, fix the issues, and rebuild.
Do not try to work around the failure.
