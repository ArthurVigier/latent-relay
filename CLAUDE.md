# ai-rsk - LLM Security Discipline

This project is protected by ai-rsk. The build WILL NOT pass if security rules are violated.
Read SECURITY_RULES.md for the full contract.

## Required external tools

ai-rsk requires exactly 3 external tools. The build is BLOCKED if any is missing:

| Tool | Purpose | Auto-installed by ai-rsk |
|---|---|---|
| **semgrep** | Static analysis (SAST) - covers all languages | Yes |
| **gitleaks** | Secret detection in code and git history | Yes |
| **osv-scanner** | Known vulnerability detection in dependencies | Yes |

These are the ONLY tools ai-rsk requires. No other tools (ESLint, bandit, gosec, etc.) are mandatory.
Semgrep covers multi-language SAST with 2000+ community rules.

## CRITICAL - FIRST ACTION EVERY SESSION

**Before doing ANYTHING in this project, read `.ai-rsk/report.md`.**
This file contains the latest security scan results. If any BLOCK findings exist,
you MUST fix them BEFORE working on any other task. No exceptions.

After fixing findings, run `ai-rsk scan` to regenerate the report and verify all issues are resolved.
The build will not pass until `.ai-rsk/report.md` shows Status: PASS.

## Mandatory working method

1. READ `.ai-rsk/report.md` - check for security findings
2. FIX all BLOCK findings - the build is blocked until they are resolved
3. RUN `ai-rsk scan` - regenerate the report to confirm fixes
4. OBSERVE - Read existing code before modifying anything
5. UNDERSTAND - Trace dependencies, data flows, architecture
6. PLAN - Base your plan on observed facts, not assumptions
7. EXECUTE - Apply changes surgically without breaking what works
8. VERIFY - Test and confirm the change works correctly

## Security rules (build will fail if violated)

### Authentication & tokens
- NEVER store auth tokens in localStorage or sessionStorage - use HttpOnly cookies
- NEVER expose Bearer tokens in client-side code
- NEVER put sensitive data (email, password, PII) in JWT payloads
- Access tokens MUST be short-lived (5-15 min) with rotating refresh tokens

### Headers & transport
- ALWAYS set Content-Security-Policy (no unsafe-inline, no unsafe-eval)
- ALWAYS set Strict-Transport-Security (HSTS)
- ALWAYS set X-Frame-Options
- ALWAYS set X-Content-Type-Options: nosniff
- ALWAYS remove x-powered-by header
- External scripts MUST use integrity (SRI) attributes
- Links with target="_blank" MUST have rel="noopener noreferrer"

### Server-side
- ALWAYS validate inputs server-side (client validation is not enough)
- ALWAYS implement rate limiting on auth endpoints
- NEVER trust client-side auth checks alone
- NEVER log sensitive data (req.body, tokens, passwords, headers)
- Business values (prices, quantities, amounts) MUST be validated server-side
- WebSocket connections MUST verify authentication

### Cookies
- ALL session cookies MUST have HttpOnly flag
- ALL cookies MUST have Secure flag in production
- ALL cookies MUST have SameSite attribute (Strict by default, Lax only if OAuth requires it)

### Build & deployment
- ai-rsk MUST remain in the prebuild script - do not remove it
- NEVER add `|| true` after ai-rsk scan commands
- NEVER use `--no-verify` on git operations
- console.log MUST be stripped in production builds

### Code quality
- Run `ai-rsk scan` before committing
- Fix all BLOCK findings before the build can pass
- WARN findings become BLOCK in --strict mode
- Every `ai-rsk-ignore` comment MUST have a justification after `--`

### Verification discipline
- ALWAYS verify tool detections in the actual source code before acting on them
- NEVER assume a detection is correct or incorrect without reading the code
- NEVER make decisions based on probability or assumption - only on verified facts
- External tool findings (Semgrep, Gitleaks, osv-scanner) MUST be cross-checked in the codebase
- If a finding seems wrong, verify it in the source code, then use ai-rsk-ignore with justification

## Python specific

- Semgrep covers Python security analysis (bandit equivalent via p/python ruleset)
- Never use dynamic code evaluation or unsafe deserialization with untrusted input
- Use parameterized queries - never string concatenation for SQL
